# ADR：Xiadie 1.0.0 范围与旧方案处置

状态：ready_for_review（作者提案）
日期：2026-10-01
决策范围：P00-U05 产品范围映射，不代表实现或发布验收。

## 决策

以归档计划包 Xiadie_V2_v1.1 的 28 条 Must、任务映射和阶段门槛作为当前产品基线。最终产品目标为 1.0.0。所有 Must 标为 1.0.0 是执行映射推导：原始 requirements.json 只有优先级、状态、阶段和任务数组，没有逐项目标版本；计划书将 P15 定义为 1.0.0-rc.1、P16 定义为 1.0.0。中间阶段提供可核验增量，不能据此把尚未验收的最终能力标成已完成。

用户产品由一个主窗口和一个面向用户的主运行时提供。ZCode 负责主运行时、对话和任务路由，ZCode 工作层实际执行权限；Core 提供角色、记忆、上下文与政策边界，不承担主路由或第二套路由；DSH 作为有界工作包的委派和执行桥接。每个组件职责、证据和权限要可追溯。避免沿用旧设计中每轮并行调用两个 Self 模型的强制路径。

## 旧设计与当前范围映射

| 旧设计内容或方向 | 当前处置 | 计划映射与边界 |
| --- | --- | --- |
| Python / FastAPI 作为产品服务实现底座 | 替换为当前计划的 ZCode 主运行时及 Core/DSH 边界；Python/FastAPI 不列为 1.0.0 强制依赖 | 保留与语言无关的数据分层、可追踪来源和恢复原则；运行时以当前锁定版本及验收卡为准。 |
| Mastra 作为 Agent 主框架，或按旧图部署两套 Self | 不作为强制技术栈；当前由 ZCode 承担面向用户的主路由，DSH 仅执行受限委派 | 不复制两套主代理或创建绕过执行端授权的平行调用链。具体组件是否采用仍由各任务隔离试验和 ADR 证据决定。 |
| 身份连续性、会话、消息、模型选择和上下文 | 保留为用户可见能力 | R01、R05、R06、R13；由 1.0.0 Must 与映射任务验收。 |
| Life、Project Memory、Dream、保留曲线和删除 | 保留为彼此有边界的能力；项目事实不受 Life 衰减，用户删除必须防止迟到任务复活 | R07、R09–R12、R16；源引用、版本、失败和恢复证据均须可检查。 |
| 子代理、团队工作、权限和工作树 | 保留受限委派和协作；执行端按真实权限和协议验证 | R02、R08、R14、R15、R17；模型初始化或协议连接不等于业务成功。 |
| 待办、文件知识、外部通信、备份及维护 | 保留，并要求权限、引用、审批和回执边界 | R20–R26；不得把草稿当成已发送，把开发目录当作发行包或把未知结果当成功。 |
| 单窗口桌面体验、固定 Live2D 角色和语音 | 保留，安排在后期阶段完成，并未从最终 Must 删除 | P10、P12、P15；Live2D/桌面外壳与语音不是 P00 核心 PoC 的前置，但 1.0.0 仍需通过真实目标应用验收。 |
| 最小 PoC 阶段不制作最终角色、语音资产 | 作为早期阶段的范围安排保留，不构成最终删减 | P00 至 P09 可使用明确标注的测试替身；测试替身不能证明 Live2D/语音能力、许可或最终产品体验。 |
| 旧文档的其他历史功能叙述 | 仅按当前 v1.1 需求和任务映射确认是否进入 1.0.0；未列入基线的不自动扩张范围 | 当前 Library 中旧需求说明书及 Mastra foundation design 正文不可用，相关历史描述为 Unverified；不以文件名、搜索摘要或旧架构草图声称原文已核验。 |

## 旧资料可信度与授权

当前可用的正式执行基线是归档计划包 Xiadie_V2_v1.1 中的项目计划书、requirements.json、任务卡、追踪矩阵及复用清单。复用清单提到的两份 Library 文件正文当前不可用，主控的来源决策记录也标为 Unverified / Source unavailable。本文对它们只说明引用关系和旧架构方向，不复述为已核实的逐字需求。

当前 1.0.0 范围不承诺手机端、多人云租户、任意角色市场、无限自治、自动群发、模型训练、游戏挂机、万能安全沙箱或全自动高质量角色建模。这些排除项来自 v1.1 计划书；未来若要纳入，须经单独范围决策，不能通过把 Must 解释为隐含要求来扩张当前计划。

进入发行范围的代码、模型、原创角色、Live2D SDK/资源和语音必须分别满足目标渠道的使用及再分发许可，并留存可审计来源、版本、哈希、许可和署名信息。许可未知时，先更换为来源清楚且允许分发的资源，或将发布判为阻断。不得把稍后补授权当成已经授权，也不得把技术 SDK 的许可扩展解释为角色资产许可。

## 后果与验收门槛

该决策让 1.0.0 的范围可以逐项追踪，同时避免早期 PoC 被误报为完整桌面产品。代价是最终阶段仍须完成真实 Windows 应用、桌面角色、语音、发行包和维护路径验证，且多个外部资源许可可能成为发布阻断项。

在 P15，逐项 Must 必须有实现版本、验收证据、许可与关键问题结论；未解决的关键问题不得冻结发行候选。在 P16，所有 Must 均须接受并获得发布授权。模型 SDK 初始化、模拟服务、单个正常案例或纯开发环境检查仅能证明其各自的有限范围。
